## 2. 改 cubicasa 路由（P0，`agent/engine_adapter.py`）

原则：**洁具和门窗由 engine 给出数字，不再让 Gemini 计数；Gemini 只回答房间类问题；厨房用先验。**

engine 返回结果里的 `method` 字段已经标明了来源，adapter 按它分流就行：

```python
from engine import answer as engine_answer, cubicasa

ROOM_CATS = {"floors", "sauna", "bedroom", "bathroom", "wc_room", "balcony"}

def answer_from_engine(path, question):
    r = engine_answer.answer(path, question)
    m = r.get("method", "")
    if m.startswith("cubicasa:vlm[yolo"):            # YOLO 结果：直接采用，不再调用 Gemini 计数
        r["source"] = "detector"
    elif m.startswith("cubicasa:prior:kitchen"):      # 厨房：先验 96%，比 Gemini 准
        r["source"] = "prior"
    elif m.startswith("cubicasa:") and cubicasa.category(question) in ROOM_CATS:
        r["source"] = "needs_vision"                   # 告诉 agent：这一题去调 count_in_drawing（Gemini）
    elif m.startswith(("swiss_dxf:", "ifc:")):
        r["source"] = "geometry"
    return r
```

在 agent 的系统提示词里加一句：
> `answer_from_engine` 返回的 `source` 是 `detector`、`prior` 或 `geometry` 时，直接用它的 `value`，不要再调用 `count_in_drawing`；只有 `source == "needs_vision"` 时才调用 `count_in_drawing`。

前端：`items[].png_bbox` 是 PNG 的像素坐标 `[x0, y0, x1, y1]`，直接画橙色编号框，和 swiss 的处理方式一样。

## 3. Nemotron 改为“一致性徽章”（P1）

现状：Nemotron 复核栅格图计数，结果是绿/黄徽章。改成：

| 情况 | 徽章 | 显示的答案 |
| --- | --- | --- |
| Nemotron 计数 = engine 计数 | 绿色 “2 independent methods agree” | engine 的值 |
| 不一致 | 黄色 “methods disagree – check boxes” | **仍然是 engine 的值**，同时显示 Nemotron 的数，以及两边的框 |
| 题目来源是 geometry（swiss/IFC） | 灰色 “exact from geometry” | 不调用 Nemotron，省下成本 |

**不要用 Nemotron 的数覆盖答案。** 数据显示，两边不一致时检测模型答对的次数是 VLM 的 3–8 倍。

## 4. “How I got this” 推理面板加字段（P1，对应可视化和成本两项评分）

每个答案的 `trace` 里补上下面这些字段：

| 字段 | 示例 | 来源 |
| --- | --- | --- |
| 答案来源 | `geometry` / `detector` / `vision LLM` / `prior` | 第 2 步的 `source` |
| 方法 | `swiss_dxf:doors`、`ifc:space_area[geometry:footprint]`、`cubicasa:vlm[yolo-cubicasa]:window` | engine 返回的 `method` |
| 证据数量 | “21 boxes” | `len(items)` |
| 耗时 | engine 耗时（毫秒），和大模型的耗时分开显示 | 已有的 `timing` |
| token 和成本 | engine 是 0 token、€0；大模型按已有的 `usage` 换算 | 已有的 `usage` |
| 警告 | “low confidence: prior” 等 | engine 返回的 `warnings` |

Pitch 里可以用的一句话：
> 85% of answers come from geometry or a 7 ms detector — zero LLM tokens; the LLM only reads rooms.

上线前用全量评测的实际比例核对这个数，不对就改。

## 5. 评测改为全量（P0，替换 `docs/eval-results.md`）

每类抽 50 题，误差大约 ±7 个百分点，看不出改动是好是坏。改用 engine 直接跑全量，不调用大模型：

```bash
export JUNCTION_DATA=/path/to/junction-dataset
python eval/run.py --source swiss_dwellings     # 约 15 s
python eval/run.py --source ifc_models          # 第一次约 1 min（建缓存），之后几秒
python eval/run.py --source cubicasa5k --split test
```

结果在 `eval/results/score_*.txt`，失败的题在 `eval/results/fails_*.jsonl`。

`--split test` 是按图片划分的 20% 留出集，训练 YOLO 时没用过。对外只报这个数。

cubicasa 的房间类题，engine 单独跑时只有先验（因为不调用 Gemini），所以 engine 的 cubicasa 分数会低于整个系统的实际分数。系统的分数等于 0 节表里“采用”那一列的组合，即 83.5%。
